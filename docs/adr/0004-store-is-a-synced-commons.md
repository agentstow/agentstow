# The Store is a synced commons; the config dir is private

`~/.agents/` is not agentstow's private directory and never was. opencode and oh-my-pi scan it natively (`Skills::Native`), Hermes Agent ships `~/.agents/skills` as the documented value for its `skills.external_dirs` setting, and the third-party `skills` CLI keeps `.skill-lock.json` in the root. The path is therefore an **interop contract** that other tools hardcode, not a naming preference — which settles three questions that would otherwise stay open:

- **The Store keeps a generic name.** A vendor-named store (`~/.agentstow/`) cannot be the commons: asking other agent authors to hardcode a path branded for one tool is a far harder sell than a neutral one, and the two agents already reading `~/.agents/` would have to be argued out of it.
- **The Store does not move under XDG.** `${XDG_DATA_HOME:-$HOME/.local/share}/agents/` is not something a competing implementation replicates identically — some honour the variable, some do not — and a commons that resolves differently per tool is not a commons. Discoverability beats convention where the entire value is that other people's tools can find it.
- **Tool configuration stays outside the Store, in `~/.agentstow/`.** The seam is git, not purity (ADR-0002 argued the weaker half): the README tells users to version the Store with git or chezmoi, so the Store is a tree meant to be committed and shared across machines, while the lock file is machine-local and `agentstow.toml` may hold per-machine tweaks. Merging them puts machine-local state inside the synced tree and immediately requires ignore rules inside a directory other tools also write to. Full XDG for the config dir would split it again — config to `$XDG_CONFIG_HOME`, lock to `$XDG_STATE_HOME` — trading one dotdir for two, in a tool whose pitch is that there is no state file.

## Consequences

- **agentstow is a tenant.** `doctor` names Store-root entries that are not its own families under "Other tools in the Store" — informational, never counted, never called an issue, never touched. It names entries and never counts *tools*, because filenames do not carry authorship: one neighbour may own three files. `status` stays silent about them, since a co-tenant has no fan-out relationship to report. `init` is unchanged and claims no ownership.
- **Dot-prefixed means different things at different layers.** Inside a family directory it is a fault (`Issue::DotPrefixed`) — a skill that was meant to be fanned out and silently will not be. At the Store root it is ordinary neighbour bookkeeping, which is exactly what a lock file should look like. The two never share vocabulary in output.
- **`AGENTSTOW_HOME` can now cause silent divergence, so it warns.** Relocating the Store cannot relocate the path a Native agent hardcodes. When the variable points somewhere other than `<home>/.agents` and a Native agent is installed, `doctor` names that agent and says it will not see this Store. The override stays: tests depend on it and multi-Store use is legitimate.
- **A registry row must be true unconditionally.** Hermes can read the Store natively, but only after a user edits `skills.external_dirs` — configuration agentstow does not write. Its row is `Skills::FanOut`, the mechanism that always works, rather than a `Native` claim that would be false on an unconfigured machine.
